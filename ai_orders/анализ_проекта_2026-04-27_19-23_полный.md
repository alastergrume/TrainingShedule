## 1. Общая информация

### 1.1 Назначение проекта
Проект представляет собой бота для формирования расписания тренировок на неделю с поддержкой Telegram и VK. Основные функции:
- Формирование недельного расписания тренировок
- Публикация расписания в мессенджерах
- Запись пользователей на тренировки
- Напоминания о тренировках
- Управление оплатами

### 1.2 Технологический стек
- **Backend**: FastAPI (Python 3.14)
- **База данных**: PostgreSQL
- **ORM**: SQLAlchemy 2.0
- **Миграции**: Alembic
- **Очереди задач**: Celery + Redis
- **Мессенджеры**: Aiogram (Telegram), VK API
- **Контейнеризация**: Docker, Docker Compose
- **Конфигурация**: Pydantic Settings

## 3. Бизнес-логика

### 3.1 Ключевые сервисы

#### ScheduleService
- **Генерация недельного расписания**: создание ScheduleEntry на основе Training шаблонов
- **Управление бронированиями**: создание, подтверждение, отмена записей
- **Получение расписания**: форматирование данных для API и мессенджеров
- **Публикация расписания**: интеграция с мессенджерами

#### AdminService
- **Управление тренировками**: CRUD операции для Training шаблонов
- **Управление расписанием**: создание и изменение конкретных ScheduleEntry
- **Модерация бронирований**: подтверждение/отклонение запросов
- **Административные действия**: логирование действий администраторов

### 3.2 Логика формирования расписания
1. **Шаблоны тренировок (Training)**: определяют день недели, время, тип, длительность
2. **Конкретные занятия (ScheduleEntry)**: генерируются на основе шаблонов для каждой недели
3. **Автоматическая генерация**: `generate_weekly_schedule()` создает записи на неделю
4. **Повторяемость**: тренировки повторяются еженедельно с возможностью исключений

### 3.3 Типы тренировок
1. **Персональные (personal)**: индивидуальные тренировки
2. **Коммерческие (commercial)**: платные групповые занятия
3. **Базовые (basic)**: бесплатные/открытые тренировки

## 4. Модели базы данных

### 4.1 Основные сущности
1. **User**: пользователи системы (Telegram/VK ID, имя, телефон, статус админа)
2. **Training**: шаблоны тренировок (тип, день недели, время, длительность)
3. **ScheduleEntry**: конкретные занятия на определенную дату
4. **Booking**: записи пользователей на тренировки
5. **Payment**: информация об оплатах
6. **Reminder**: напоминания о тренировках
7. **PublishedSchedule**: опубликованные расписания
8. **AdminAction**: логи административных действий

### 4.2 Enum типы
- **TrainingType**: personal, commercial, basic
- **BookingStatus**: pending, confirmed, cancelled, attended
- **AdminActionType**: 11 типов действий (создание, обновление, удаление и т.д.)
- **MessengerType**: telegram, vk
- **ReminderStatus**: pending, sent, failed

### 4.3 Связи между таблицами
- User 1:N Booking
- Training 1:N ScheduleEntry
- ScheduleEntry 1:N Booking
- Booking 1:1 Payment
- Booking 1:N Reminder

## 5. API Endpoints

### 5.1 Публичные endpoints
- `GET /` - информация о API
- `GET /health` - проверка здоровья
- `GET /api/schedule/week` - получение недельного расписания
- `POST /api/bookings` - создание бронирования

### 5.2 Административные endpoints
- `GET /api/admin/trainings` - получение всех тренировок
- `POST /api/admin/trainings` - создание тренировки
- `PUT /api/admin/trainings/{id}` - обновление тренировки
- `DELETE /api/admin/trainings/{id}` - удаление тренировки
- `POST /api/admin/schedule-entries` - создание записи расписания
- `GET /api/admin/bookings/pending` - ожидающие бронирования
- `POST /api/admin/bookings/{id}/confirm` - подтверждение бронирования
- `POST /api/admin/bookings/{id}/reject` - отклонение бронирования

### 5.3 Особенности API
- **Аутентификация**: в текущей реализации используется заглушка `admin_id=1`
- **Валидация**: через Pydantic схемы в `src/business_logic/schemas/`
- **Обработка ошибок**: стандартные HTTP коды и сообщения об ошибках
- **CORS**: разрешены все origins (для разработки)

## 6. Интеграция с мессенджерами

### 6.1 Архитектура интеграции
- **Абстрактный интерфейс**: `MessengerInterface` определяет общие методы
- **Фабрика**: `MessengerFactory` создает экземпляры мессенджеров
- **Поддерживаемые платформы**: Telegram, VK

### 6.2 Реализованные функции
1. **Отправка сообщений**: текстовые сообщения пользователям и в каналы
2. **Редактирование сообщений**: обновление опубликованного расписания
3. **Отправка расписания**: форматирование и публикация недельного расписания
4. **Напоминания**: отправка уведомлений перед тренировками
5. **Получение информации о пользователе**: идентификация по ID мессенджера

### 6.3 Конфигурация
- **Telegram**: токен бота, ID канала, ID администраторов
- **VK**: токен группы, ID группы, код подтверждения, секретный ключ

## 9. Анализ качества кода

### 9.1 Сильные стороны
1. **Чистая архитектура**: четкое разделение ответственности
2. **Типизация**: использование Enum вместо строковых констант
3. **Документация**: подробные docstrings и README
4. **Масштабируемость**: поддержка multiple messengers через интерфейсы
5. **Контейнеризация**: полная Docker поддержка
6. **Миграции**: правильная настройка Alembic с версионированием

### 9.2 Области для улучшения
1. **Аутентификация**: отсутствует система аутентификации (используется заглушка admin_id=1)
2. **Тестирование**: нет unit-тестов для бизнес-логики
3. **N+1 запросы**: в `get_week_schedule()` есть потенциальные проблемы производительности
4. **Обработка ошибок**: можно улучшить обработку исключений в сервисах
5. **Валидация времени**: хранение времени как строки "HH:MM" вместо типа time

### 9.3 Потенциальные уязвимости
1. **CORS**: разрешены все origins (`allow_origins=["*"]`)
2. **Секретные ключи**: SECRET_KEY имеет значение по умолчанию
3. **Отсутствие rate limiting**: нет ограничений на частоту запросов
4. **SQL инъекции**: используются параметризованные запросы через SQLAlchemy (безопасно)
